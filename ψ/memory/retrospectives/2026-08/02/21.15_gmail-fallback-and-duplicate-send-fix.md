## AI Diary

This was a genuinely long session and I want to be honest about where my confidence was earned versus assumed. The SMTP diagnosis felt solid because I didn't stop at "it failed" — I went down to raw sockets, tested against a non-Gmail host to rule out general TLS breakage, and then found a teammate's independent A/B test confirming the same finding before I'd even read their work. That convergent evidence from two different methods is the kind of thing that made me actually trust the diagnosis instead of just hoping it was right.

The duplicate-send bug is the moment I'm most glad I did a *real* send instead of stopping at "the code looks correct" or "the dry-run works." I had already written the Gmail API fallback, tested it with mocks, and could have reported "done" — the mocked tests all passed. But mocks don't reproduce the specific failure mode of "the real operation succeeded but the polite goodbye handshake didn't" — that only showed up because I checked the actual inbox via IMAP and counted 4 emails instead of 2. If I'd trusted the "Send result: sent" log line alone, I would have shipped a bug that duplicates every single email this pipeline ever sends, forever, any time the network hiccups during QUIT. That's a bad kind of forever-bug because it's silent — the code path reports success on both attempts.

I also want to name a real uncertainty: I don't have full confidence in the current state of AC5 (offline soft-fail). I started a legitimate test (dead-proxy trick to simulate network-down, which is a reasonable technique given no sudo access), watched it work through several retry cycles across the 6-section Gemini calls, and then lost the output when the session moved to `/model` switches and eventually `/rrr`. - Writing a regression test and *proving* it catches the bug (running it against pre-fix code, watching it fail with the exact symptom, then confirming the fix) rather than just writing a test that happens to pass.

## What Could Improve

- I lost track of the AC5 verification's actual outcome because I let a long-running background process's log file live only in `/tmp`, which apparently got cleared across a session/model boundary. Should have written offline-test output to a path inside the repo (or at minimum somewhere more durable than bare `/tmp`) given how long these pipeline runs take (10+ minutes routinely).
- The offline-simulation approach (dead proxy) doesn't actually cover every code path — the Claude CLI fallback tier's `subprocess.run(["claude", "-p", ...])` doesn't go through `HTTP_PROXY`/`HTTPS_PROXY` env vars at all (it has its own network stack), so "fully offline" wasn't actually fully offline for that tier. If I'd thought about it before running, I could have designed a tighter test or documented that gap explicitly instead of discovering it mid-run.
- I should have proactively saved intermediate state (like this retro, or a shorter progress note) earlier in a session this long, rather than only at the point the user explicitly asked. A session spanning this many hours and this many real bugs found deserves checkpointing along the way, not just at the end.

## Lessons Learned

Promoted as a semantic learning (see `ψ/memory/learnings/`): mocked/unit-test-green does not prove a real integration works — verify network-facing code (email send, API calls) with a real call and an independent verification channel (IMAP inbox check, not just the sender's own "success" return value) at least once before calling it done. This is the second time in this specific codebase's history this exact lesson would apply (the original SMTP retry-without-resend-guard bug, and now this QUIT-handshake variant) — worth watching for a third occurrence that would justify a procedural rule (e.g., "network-send functions must be idempotent by design, not just retried carefully").
