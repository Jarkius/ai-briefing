## Lessons Learned

- When a user requests a `.gitignore` change for a path, run `git ls-files <path>` (or `git status`) *before* editing the ignore file — the correct fix depends entirely on whether files under that path are already tracked. Ignoring a path with existing tracked files creates inconsistent history without removing anything, which is a common oversight in any repo, not just this one.
- When a repo name a user mentions doesn't resolve on the first lookup, check for near-miss matches (same base name under different orgs/accounts, local directories) before reporting "not found" — the user is often referring to a real thing with an imprecise name, not a nonexistent one.
- Mid-turn user messages injected via system-reminder during an unrelated flow (like a retro/skill invocation) should be actioned immediately if simple and low-risk, even while a multi-step skill process is in progress — don't defer a one-line request just because a skill's step sequence is underway.
